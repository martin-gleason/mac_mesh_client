# F1 — The soak test tool

**Kind:** feature · **Milestone:** v0.1 · **Priority:** P0
**Status:** **written, awaiting gate `G4`. Nothing here is built.**
**Learning dial:** **50-50** (`D1`). Four of seven tasks are `owner: human`, and they are
all the Python.

> **Written before the code, and waiting.** This is the moment the gate exists for — the
> cheap point at which the owner can say *don't build that*, or *build the smaller version*.
> Stacked on `C1/harness`, which is open as PR #1 and not yet merged.

---

## What this is for

**One question, and the tool exists only to answer it:**

> Does a persistently held TCP connection to the V4 degrade the radio over time?

`RR1` is why. Upstream `meshtastic/firmware#9632` reports a persistent TCP client crashing a
V4 roughly every 90 minutes on 2.7.15/2.7.19. It is closed, and this radio runs 2.7.26 — but
a long-lived client is exactly the shape that provoked it, and **the daemon architecture in
`FR11` is a long-lived client by definition.** If the answer is bad, v0.5's shape changes.

The tool is an instrument, not a product. Its output is a log somebody has to trust at hour
40, which is the whole design constraint.

**It is also the learning unit.** The agent writes the scaffold and the tests; the owner
writes the implementations. The tests are the contract — **a failing test is not a wrong
test.**

## Tasks

### Foundational — delivers nothing user-visible

**`F1-T1` · agent · the fake radio and the seam it plugs into**

No test may touch the V4 (`docs/conventions-local.md`). So the sampler takes its radio as a
dependency rather than constructing a `TCPInterface`, and a fake supplies snapshots on
demand — including the ones that matter and are almost impossible to provoke on real
hardware: a reboot (uptime stepping backwards), a heap trending down, a node DB collapsing
toward zero, a disconnect, a disconnect that never recovers.

**Checkpoint:** a test drives a full sample cycle, and can produce all five degradation
shapes above, with no hardware and no network.

Ratifies `D13`, currently `proposed`.

### Vertical slices — each one a checkpoint you can hold

**`F1-T2` · human · the sample record** — `FR4`, `FR5`

One radio snapshot in, one immutable record out: node count, node identity, uptime counter,
reported free heap, connection state, timestamp. **Position packets are counted and their
coordinates are never stored** (`FR5`) — the record has no field to put them in, which is a
stronger guarantee than a rule about not filling one in.

Pure function, no I/O, no clock of its own. That is deliberate: it is the piece that is
testable without anything, and it is the right first thing to write in a new language.

**Checkpoint:** given a fake snapshot, the record is exactly right; given a snapshot with
positions, the count is right and no coordinate appears anywhere in the output.

**`F1-T3` · human · the sampling loop and the two windows** — `FR1`, `FR2`, `FR3`

30-second cadence (`D10`). 36h passive, then 12h active (`D4`). Ordering is load-bearing:
passive first, or a failure in the active window cannot be attributed between elapsed time
and self-inflicted load. In the active window, heartbeats on a cadence in tens of minutes
with `hop_limit` reduced so the mesh does not rebroadcast test traffic; every send timestamped.

**The clock is injected.** A test that takes 48 hours is not a test.

**Checkpoint:** a 48-hour run completes in milliseconds against a fake clock, with the
window boundary landing exactly where `FR2` says and the heartbeat count exactly what the
cadence implies.

**`F1-T4` · human · reconnect, backoff, and the event log** — `FR6`

Capped backoff. **Every disconnect and every reconnect is its own timestamped event.**
Unrecovered means not restored within five minutes, and that fails criterion 2 (`D3`).

Never silent — a silent reconnect papers over the exact failure being hunted. Note `NFR9`:
this rule governs the **radio** only; retrying a spreadsheet write is a different rule and
is correct.

**Checkpoint:** a fake that drops at a known time and returns 90 seconds later produces two
events and does not fail the run; one that drops and never returns fails criterion 2, and
the failure names the minute it happened.

**`F1-T5` · human · the Sheets writer** — `FR7`, `FR8`

`google-api-python-client` (`D11`), batched rather than one call per sample — at a 30-second
cadence that is roughly two writes a minute, so batching is about not being fragile rather
than about quota. **Flush on shutdown**, without which the tail of the run is lost, and the
tail is where degradation shows.

The learning here is the transferable part: an API client, batching, and a context manager
or `finally` that actually runs.

**Checkpoint:** a run interrupted mid-batch has every sample in the sheet.

**`F1-T6` · human · the fallback path and the logger's own failures** — `FR7`, `FR9`

When the remote write fails, the sample lands in a local file. **And the logger logs its own
write failures**, so a gap in the data is attributable: *"logger could not write"* must be
distinguishable from *"radio was down"* or none of the four criteria can be evaluated.

**This is the task the run's trustworthiness actually rests on**, and it is separated from
`F1-T5` for that reason — `RR2` is the risk that a gap is ambiguous, and this is its
mitigation.

**Checkpoint:** with the network refused, no sample is lost and the log says why; the
resulting record is distinguishable from one where the radio went away.

**`F1-T7` · agent · the run harness, the run record, and the credentials**

Entry point, `--dry-run` for the two-hour rehearsal, and a run record that states the
**power condition** — TX power setting, battery attached or not (`FR10`, `RR9`). Variable
control, not a claim about cause: two hypotheses exist for the observed instability and
neither has evidence, and the soak can only separate them if this is held constant and
stated. Plus a run id, so two runs cannot be mistaken for one in a shared sheet.

Console work is the agent's per the intent — service account, API enablement, key placement
at `~/.config` mode `0600`, sheet permissions — **except the parts only the owner can do**,
which are `O11`.

**Checkpoint:** `--dry-run` completes a two-hour rehearsal end to end and the sheet has what
it should.

## Seven tasks, not six

`conventions.md` observes four to six as the working size. This is seven, and the extra one
is deliberate: `F1-T6` was split out of `F1-T5` because *"the write path works"* and *"a gap
in the data is attributable"* are different claims, and the second is the one `RR2` is about.
Folding it back in would hide the risk inside a task named after something else.

## Open questions for the gate

Asked one at a time (`turing-review:D69`), not as a wall. Listed here so the set is visible;
an item that comes back unanswered stays **open**, never assumed.

1. ~~**Heartbeat cadence in the active window.**~~ **Answered 2026-09-10: 30 minutes.**
   24 sends across the 12-hour active window. The passive window carries the evidence; the
   active window only has to prove the send path still works.
2. ~~**`hop_limit` for heartbeats.**~~ **Answered 2026-09-10: `0` — no rebroadcast at all.**
   This plan first proposed `1`, which was wrong: `1` permits exactly one rebroadcast, so
   the mesh relays the traffic `FR3` says not to relay. `0` matches the requirement's own
   words and is the minimum airtime cost on a channel with ~215 nodes in range (`NFR2`).
   Verified the library honours it rather than treating it as unset:
   `mesh_interface.py:1012` reads `if hopLimit is not None`, so `0` reaches
   `meshPacket.hop_limit`. **Known limit, not a defect:** a broadcast is never ACKed, so a
   heartbeat proves the radio formed and transmitted a packet, not that anybody heard it.
   That gap is `O6` and is inherent to broadcast at any hop limit.
3. ~~**Where does the local fallback file live?**~~ **Answered 2026-09-10:
   `~/.local/share/mesh-client/`.** Consistent with the `~/.config` credential path in
   `NFR7` — config in one place, data in the other, both outside the repo. No `.gitignore`
   rule is load-bearing for data safety, and `git clean -xdf` cannot reach it.
4. ~~**Does the spreadsheet already exist?**~~ **Resolved by investigation, not asked.** No
   spreadsheet matching mesh/soak/meshtastic exists in the owner's Drive.
   **Decided by the agent, overturnable:** the **owner** creates the sheet and shares it
   with the service-account address as Editor; `F1-T7` takes a sheet id from config and
   never creates one. The reason is a specific trap: a sheet created *by* a service account
   is owned by that service account and lives in a Drive no human can open — it does not
   appear in the owner's Drive at all unless separately shared back, and diagnosing that at
   hour 20 of a soak is exactly the failure `RR2` describes. A sheet the owner owns and
   lends to the robot inverts that. The sheet id lives in `~/.config`, not the repository.
5. ~~**Is the two-hour dry run its own gate?**~~ **Answered 2026-09-10: its own gate,
   after `F1` merges.** `F1` ships when the tool is built, reviewed and green. The dry run
   is a separate authorised event with its own recorded outcome — it is the first moment
   real credentials, the real sheet and the real radio are all involved at once, and any of
   the three can fail in ways no unit test predicts. Tracked as `G5`.

**All five answered. Nothing on this list is outstanding**, which is what lets the gate be
crossed on the plan as written rather than on a plan with holes in it.

## Definition of done

- All seven checkpoints demonstrated, each with output.
- Every `FR1`–`FR10` traced to a test; every test citing an `FR` or a `D`.
- **At least one new mutation per behaviour the tests protect**, run and seen to fail
  (`NFR8`). The reconnect logic and the fallback path are the two that most need it — both
  are error paths, and error paths are where a green suite is most likely to be lying.
- The floor raised in the same commit that adds the assertions.
- Adversarial review logged at `docs/reviews/F1.md`.
- **The tool is not the result.** `F1` ships when the tool runs unattended and produces a log
  worth trusting. **Three separate events, three separate gates:** `F1` the tool · `G5` the
  two-hour dry run against real credentials and real hardware · the 48-hour result, which is
  what the ladder gates v0.5 on.
